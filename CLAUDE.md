## Project identity

- **Name:** ANIME//SIM
- **One-sentence description:** An original, unofficial fan-made prototype —
  a story-driven 2D anime life simulator blending a visual novel, a
  lightweight social-strategy game, and a compact turn-based RPG, across two
  original branching worlds.
- **Detailed summary:** Players build a custom protagonist in a full
  character creator, then drop into one of two original worlds: **Elite
  Academy** (a psychological, competitive boarding-school drama about class
  rankings and quiet manipulation) or **Aincrad** (a survival-tactical
  floating-castle MMO where logout is disabled and boss raids have real
  consequences). Both worlds share one dialogue/relationship/quest/combat
  engine driven entirely by typed, Zod-validated content data. **No
  copyrighted artwork, music, dialogue, scripts, or character likenesses are
  used anywhere** — every character, location, item, and line of dialogue is
  an original creation (see `README.md` → Asset & License Notes).
- **Target audience:** Solo players who enjoy visual-novel-style branching
  narrative with light RPG/combat systems; a personal/portfolio project, not
  a commercial product.
- **Current development stage:** Full 10-chapter/10-floor content arc in
  both worlds, as of commit `4f6ac3e`. Elite Academy Chapters 1–10 (a full
  school year) and Aincrad Floors 1–10 (Town of Beginnings through The
  Tenth Gate) are each fully playable and chained together via a
  chapter-navigation system wired into the recap screen ("Next Chapter"
  button) and the in-game device (a Chapters tab for jumping back to any
  unlocked chapter). Chapters 2–10 in both worlds are moderate-depth (one
  arrival beat, one or two character beats, one decision, one close) by
  design, per `patchnotes.ts`'s own `v0.2.0` known-issues note — Chapter
  One in each world remains the deepest single chapter. See
  `PROJECT_STATE.md` and `TASKS.md`.
- **Production status:** **Not deployed.** The repository has a GitHub
  remote (`https://github.com/Gariyuuu/anime-sim.git`, branch `main`, in
  sync with `origin/main` for the one existing commit) but there is no
  `.vercel/` directory, no `vercel.json`, and no deployed URL referenced
  anywhere in the repo. Despite `README.md`'s "Deployment" section
  describing a zero-config Vercel deploy, that deploy has evidently never
  been run from this machine/repo. Do not assume a live URL exists.
- **Repository type:** Single Next.js app, not a monorepo. `pnpm-workspace.yaml`
  exists but only contains `allowBuilds` package-approval settings — it does
  not declare any actual workspace packages; there is exactly one
  `package.json` at the repo root.
- **Important scope note:** `~/Projects` (the parent of this repo) is

**What should NOT be placed where:**
- `content/` files must stay plain, side-effect-free data (`*Input` typed
  objects) — they must not import from `components/` or `state/`. This is
  the one architectural invariant `README.md` calls out explicitly and it
  holds true across the whole codebase as of this audit.
- Game-rule logic belongs in `lib/` (pure functions operating on a
  `SaveGame`) or `engine/` (pure functions operating on combat/exploration
  runtime state) — not inside React components, and not inline in
  `gameStore.ts` action bodies beyond orchestration.
- Do not add a second Zustand store, a Redux store, or React Context for
  global state — `useGameStore` is the only one and the whole app assumes
  that.

## Architecture summary

See `ARCHITECTURE.md` for the full write-up with a Mermaid diagram. Short
version:

- **Fully client-side SPA.** No server routes (`src/app/api/` does not
  exist), no database server, no required environment variables. Everything
  — including "persistence" — runs in the browser.
- **One Zustand store** (`src/state/gameStore.ts`) holds the entire runtime
  state: which screen is showing, the active `SaveGame` object, the active
  `CombatRuntimeState`, notifications, and debug-panel state. Components
  read via selectors and call store actions; components never mutate
  `SaveGame` directly.
- **Content is data, not code.** `src/content/worlds/<world>/*.ts` are plain
  TypeScript arrays of `*Input`-typed objects (NPCs, items, quests, maps,
  scenes, enemies, …), aggregated and validated once at import time by
  `src/content/registry.ts` via `zod`'s `.parse()` — an invalid or
  malformed content object throws at import time (`pnpm dev`/`pnpm build`),
  not silently at runtime.
- **Game rules are pure functions.** `src/lib/conditions.ts`
  (`evaluateConditions`) and `src/lib/effects.ts` (`applyEffects`) take a
  `SaveGame` and a `Condition[]`/`Effect[]` and return a boolean / a new
  `SaveGame` + side-effect commands, respectively — no React, no I/O.
  `src/engine/combat.ts` and `src/engine/exploration.ts` are the same
  pattern for combat/movement.
- **Persistence is Dexie/IndexedDB**, one `saves` table keyed by `slotId`,
  every write and read re-validated through `SaveGameSchema` (`lib/save.ts`,
  `lib/db.ts`). See `DATABASE.md`.

## Coding conventions

These are **Verified** (observed consistently across the existing codebase)
unless marked Inferred/Recommended.

- **Naming:** `camelCase` for functions/variables, `PascalCase` for React
  components and TS types, file names match their default export
  (`PascalCase.tsx` for components, `camelCase.ts` for plain modules).
  Content IDs are prefixed by world (`ea-` for Elite Academy, `ai-` for
  Aincrad) and kind (`ea-npc-…`, `ea-scene-…`, `ai-enc-…`, `ai-flag-…`, …).
- **Imports:** Path alias `@/*` → `src/*` (configured in `tsconfig.json` and
  `vitest.config.mts`) used everywhere.
- **Components:** Function components only, no class components. Every
  component that uses hooks/state/effects is explicitly marked `"use
  client"` at the top (the whole app is effectively client-rendered — there
  is exactly one Server Component, `src/app/layout.tsx`, which is a Server
  Component only because it doesn't need hooks; `src/app/page.tsx` is also
  a Server Component but only renders the client `GameRoot`).
- **Content authoring:** New NPCs/items/quests/maps/scenes/enemies are
  added as plain object literals to the relevant `content/worlds/<world>/`
  file, typed against the `*Input` Zod-inferred type, and referenced by
  `id` from wherever needed — nothing needs a second registration step,
  `registry.ts` aggregates every world's arrays automatically (see
  `README.md` → Content-Authoring Guide for the full authoring spec,
  which is accurate and detailed).
- **State mutations:** All `SaveGame` mutations go through
  `applyEffects()`/`evaluateConditions()` (`lib/effects.ts`,
  `lib/conditions.ts`) or through named `gameStore.ts` actions — never
  mutate a `SaveGame` object component-side. `applyEffects` itself uses
  `structuredClone` and mutates the clone, returning a new object (not a
  fully-immutable/Immer-style pattern, but the caller always receives a
  fresh reference).
- **Combat/exploration runtime:** Same pattern — `engine/combat.ts`
  functions take a `CombatRuntimeState`, deep-clone it
  (`structuredCloneState`), mutate the clone, and return it.
- **Types:** `strict: true` in `tsconfig.json`. Content shapes are defined
  once as a Zod schema (`types/*.ts`) with both the full type (`z.infer`)
  and an "Input" convenience type (`z.input`, via `types/content-input.ts`)
  that makes `.default()`-backed fields optional for content authors — see
  `types/content-input.ts`'s own doc comment for why this exists.
- **Error handling:** No custom error classes. Zod's `.parse()` throwing on
  invalid content at import time is the primary "fail loudly, fail early"
  mechanism; `.safeParse()` is used instead wherever bad *runtime* data
  (a corrupted/hand-edited save, a settings blob from `localStorage`)
  should degrade gracefully rather than crash (`lib/save.ts`
  `loadSaveSlot`, `GameRoot.tsx`'s settings load).
- **Comments:** Sparse. A few multi-line JSDoc comments on the trickier
  store internals (`_resolveEffects`, `_settleAtNode` in `gameStore.ts`)
  and on `content-input.ts`. No per-file docblocks.
- **Tests:** One `*.test.ts` file per concern under `src/tests/`
  (conditions, effects, combat, save, dialogueEngine, chapterOutcomes),
  plus a shared `fixtures.ts` (`makeSave()` helper). No component/UI tests
  exist — see `TESTING.md`.

## Database summary

There is no relational, document, or server-hosted database of any kind.
See `DATABASE.md` for the full write-up. In short: one Dexie
(IndexedDB-wrapper) database, `anime-sim-db`, one table (`saves`, keyed by
`slotId`, indexed on `worldId`/`updatedAt`), storing the entire
`SaveGame` object per slot as a single record. Every write and read is
validated against `SaveGameSchema` (Zod). No migrations beyond Dexie's own
`version(1)` declaration. No server-side access control of any kind (it's
purely client-local storage — see `SECURITY.md`).

## Critical rules — DO NOT CHANGE WITHOUT REVIEW

- **`src/content/registry.ts`'s `parseAll`/schema wiring** — every content
  array is validated once at import time. Do not bypass `parseAll` or add
  raw (unvalidated) content arrays; an invalid object should fail loudly at
  build/dev time, not silently produce `undefined` lookups at runtime.
- **`SaveGameSchema` (`src/types/save.ts`)** — this is the on-disk (IndexedDB)
  save format. Adding a required (non-`.default()`, non-`.optional()`)
  field breaks `loadSaveSlot`'s `safeParse` for any previously-saved game
  (returns `null`, i.e. the save silently fails to load) and breaks
  `importSave`'s `.parse()` (throws) for any previously-exported save file.
  Always add new fields as `.optional()` or `.default(...)`, exactly as the
  in-progress `unlockedChapterIds` field already does it correctly — the
  bug in the current uncommitted diff is that the test fixture (not the
  schema) wasn't updated, not that the schema itself is unsafe.
- **`applyEffects`/`evaluateConditions` (`src/lib/effects.ts`,
  `src/lib/conditions.ts`) and the `Effect`/`Condition` unions
  (`src/types/narrative.ts`)** — these are the single execution path for
  every stat/relationship/flag/quest/inventory change across both worlds'
  entire scene content. A behavior change here silently changes the outcome
  of every authored scene that uses that effect/condition type.
- **`_resolveEffects`/`_settleAtNode` (`src/state/gameStore.ts`)** — the
  scene-navigation/effect-settling pipeline every dialogue choice and map
  interaction routes through. Subtle bugs here (e.g. re-ordering when
  `saveGame()` is called relative to `set()`) can silently drop player
  progress.
- **Do not commit real secret values.** There is currently no `.env` file
  and nothing sensitive to leak, but if `NEXT_PUBLIC_ENABLE_DEBUG` or any
  future env var handling is added, keep the "no real values in git"
  discipline used elsewhere in this developer's other repos.
